# 项目二：把视频中的可疑变化变成可回放、可核验的事件

你接到一段短视频，反馈是“中间卡了一下，后面又闪了”。交付一张截图还不够：同事需要知道原文件是哪一版、异常在什么时间、是否属于有意静止或切镜，以及改动后有没有减少误报。本章用 `video-temporal-audit` 完成这条工作链。输入是本机视频文件与检测配置；输出是逐帧记录、候选事件、无声预览、中文时间线和独立复核记录。最终可演示“点击事件—连续回看—写理由—导出—重新导入”，并用事件数量解释算法改动。

这对应视频效果评测中的故障定位、正常镜头误报分析、回归复测和证据交接。这里的“回归”是修改程序后用固定材料检查原行为有没有退化，不是统计学的回归模型。工具使用图像差值与运动几何，不运行视频生成模型，不下载神经网络权重。附带素材是程序画出的几何视频，标签是构造事件；独立真人质量评分为0。合成集可以检验一个具体机制，不能代表全行业视频能力，也不能说明某个生成模型的身份保持、物理合理性或口型水平。

本章属于完整50周路线中的第35—38周，每周约15小时，共60小时；前30周基础已另计450小时。先复习第5—6周的路径、函数和JSON，第10—11周的分母与控制变量，第19—21周的镜头、帧和时间。暂时不会矩阵运算也能开始：先理解“上一帧向右搬三个像素后，与下一帧是否更相似”，再看实现。验收依靠实际产物和解释，不靠运行一次脚本宣称掌握。

## 三、时间先用秒解释，再看帧序号

帧是视频中的一张图。帧序号0、1、2只是解码后的顺序；PTS是“这张图应在何时显示”的时间戳。本工具将PTS换成秒，并保留源文件的起点。恒定帧率且起点已知时，才可能用帧序号和固定间隔换算；VFR表示可变帧率，相邻帧间隔可以不同。

纸上写出三帧：源PTS为5.00、5.10、5.40秒。相对播放位置分别是0.00、0.10、0.40秒，前两帧显示时长为0.10、0.30秒。第三帧即使序号是2，也不能随便用 `2/10=0.20`秒代替实际0.40秒。统一公式是：

```text
相对播放秒数 = 源PTS秒数 - 源首帧PTS秒数
事件持续秒数 = 事件结束源PTS - 事件开始源PTS
```

实际 `timing/offset_flash/report.json`中首帧为5.0秒，事件为源坐标7.0—7.25秒，因此页面显示播放2.0—2.25秒。回放按钮提前0.5秒，让你看到变化前的状态，定位目标是1.5秒。合法负PTS也可以这样平移；程序拒绝的是不递增或非有限时间，不是一概拒绝负起点。

`media.py`的 `decode_video()`输入文件路径，调用同一次FFmpeg解码，同时输出PNG与 `showinfo` 时间记录。程序检查帧数与时间行数一致，再生成 `source_pts_s`、`relative_pts_s`、`durations_s`。不是另抽一次图片、猜一次帧率后强行配对。前面各帧的时长由下一帧PTS减当前PTS得到；最后一帧没有“下一帧”，优先采用实际正显示时长，否则多帧片用相邻间隔中位数估计，单帧又没有有效时长则拒绝。

尾帧必须单独说明。`offset_flash`原始MP4的既有独立FFprobe流时长是3.916667秒；源末帧缺少正显示时长。分析估计它再显示约0.083333秒，于是分析相对结束为4.0秒、源坐标结束为9.0秒。报告保存 `source_end_is_estimated=true`、`timing_warnings`，预览保存 `source_last_duration_source=median_delta_ESTIMATE`。不能把4.0秒写成源文件实测时长。

曾经预览只核对帧开始时间，遗漏末帧的显示长度，造成末尾提前结束。修复后的 `make_preview()`显式写入末包时长，并重新解码检查帧数、每帧开始、尾帧时长和结束位置；预览尾时长必须实际读到正值，不能再用估计证明自己。该例预览读回结束4.0000003秒。0.00003秒是编码时间映射的验收容差，不是检测故障边界的准确率或精度承诺。

## 四、三个事件来自怎样的数字

解码图先保持比例缩小到320×192边界内，再把RGB三个通道变成 `0.2126R+0.7152G+0.0722B`的强度代理。它使用编码颜色值，不是经过仪器标定的物理亮度。`core.py`的 `frame_features()`接收RGB数组列表，输出每帧均值 `luma_proxy`、相邻帧差 `mae`、均值变化 `brightness_delta`和结构差 `structure_mae`。

先手算MAE：前一帧两个像素是10、30，后一帧是12、34，平均绝对差为 `(2+4)/2=3`。如果很长一段相邻MAE都很小，`detect_events()`用源PTS计算持续长度，达到 `freeze_min_s`才输出 `freeze_candidate`。冻结仍是“静止候选”：字幕卡、故意停格与真正卡顿都可能相同。两帧覆盖一秒可能达到时长门槛，二十帧只覆盖0.2秒可能达不到；帧数多不等于持续时间长。

亮度事件先比较整帧均值。均值从60变125，变化65，超过本例阈值20。闪光进入与退出往往各产生一个边缘，程序把相近边缘按 `flash_merge_gap_s`合并，因此候选区间可能宽于实际闪光。代码事件名是 `brightness_jump`，本章称亮度突变；这不保证每一次报警都是有害闪烁，合法摄影闪光也需要任务规则解释。

切镜先比较去掉各自均值后的空间图案。例如整帧均匀加亮，减去均值后图案可基本不变；换成另一张背景，图案差仍明显。结构差越过门槛会产生 `shot_cut_candidate`，邻近边缘只保留较强者。切镜附近0.2秒内的亮度边缘会被保护规则抑制，避免正常切换明暗场景产生闪烁报警。这个决定也可能压掉真实闪光，后面必须检查漏检。

三类输出都包含 `type`、`start_s`、`end_s`、证据帧序号和分数。`report.py`的 `analyze_video()`为事件添加E001等编号、播放坐标和证据图。分数只是相应规则的测量值，不可把65理解成“65%确定有问题”。

## 五、为什么平移会误报，以及运动补偿怎样工作

假设前一帧是一面砖墙，后一帧整体向右移动三像素。直接比较同一坐标，会拿上一块砖与下一块砖比较，结构差很大，像切镜；但观众看到的是连续摇镜。运动补偿先估计两帧之间的几何变换，把前帧对齐后再比较。它在检测用的小图上工作，原视频与源PTS不被改写。

`motion.py`的 `estimate_motion()`先用 `goodFeaturesToTrack`最多找180个角点。角点是局部图案明显、便于重新寻找的位置，例如砖缝交点；纯色墙面往往找不到足够点。接着用 `calcOpticalFlowPyrLK`从前帧追踪到后帧。这里的光流是图像点位置的估计变化，不是识别物体名称。函数接口及金字塔Lucas–Kanade方法见[OpenCV官方跟踪文档](https://docs.opencv.org/4.13.0/dc/d6b/group__video__track.html)。

只向前追踪可能认错点，所以再从后帧追踪回来。假设点从 `(10,20)`到 `(13,20)`，反向回到 `(10.4,20)`，往返误差0.4像素，小于1.5像素门槛，保留；如果回到 `(14,20)`，误差4像素，就剔除。两个方向都必须追踪成功，最后至少留下10条轨迹，才进入拟合。这叫前后向检验，其作用是筛掉不自洽对应，不保证留下的点一定正确。

RANSAC从对应点中尝试解释多数点共同运动的变换，把不符合者视为外点。例如十二点里十点右移三像素、两点属于另行运动的小球，共同右移有望成为背景运动估计。`estimateAffinePartial2D`允许平移、旋转和均匀缩放，输出2×3变换矩阵与内点标记；它不能解释任意透视变化。函数范围见[OpenCV官方几何估计文档](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html)。

本项目还要求至少8内点、内点率至少0.55、尺度在0.90—1.10之间、有效重叠至少0.60。对齐后只在两帧有效相交区域计算中心化残差，并收缩边缘，避免把变换产生的填充黑边算成差异。成功时 `motion_status=ok`，补偿残差可以替换切镜分数；弱纹理、轨迹不足、尺度越界等失败时，残差为 `null`，回退原结构差，不能把失败当作零变化。

特别注意：冻结始终使用原始MAE。否则砖墙平移对齐后几乎相同，程序可能反过来声称“画面冻结”。这就是不同指标回答不同问题：原始差回答画面有没有变化，补偿残差回答共同运动解释后还剩什么差异。多物体独立运动、视差和遮挡都可能破坏单一全局变换；已有20片测试中940对相邻帧有103对拟合失败，失败记录保留在分母内。

## 七、事件怎样匹配：先手算，再运行函数

参考事件是标注或构造的应有区间，预测事件是程序输出的候选。匹配限制在同一视频、同一类型，并且一条预测最多对应一条参考。区间采用 `[开始,结束)`：包含开始，不包含结束，因此 `[5,6)`与 `[6,7)`只接壤，重叠时长为0。时间交并比tIoU等于交集时长除以并集时长。预测 `[2,2.25)`、参考 `[2,2.166667)`时，约为 `0.166667/0.25=0.667`，达到当前0.3门槛。

不能只挑最高tIoU然后不再回头。设同类型预测P1=`[0,6)`、P2=`[0,4)`、P3=`[5,9)`；参考T1=`[0,5)`、T2=`[4,7)`、T3=`[7,9)`。下表每格按交集/并集手算：

|预测|T1|T2|T3|
|---|---:|---:|---:|
|P1|5/6|2/7|0|
|P2|4/5|0|0|
|P3|0|2/5|1/2|

这一纸笔例单独设门槛0.25。最高分P1—T1为5/6，贪心先取它，P2就无处可配；再取P3—T3，最后只有2对。允许重新分配时，取P1—T2、P2—T1、P3—T3，可以得到3对，总tIoU为 `2/7+4/5+1/2=1.585714`。当前协议先最大化匹配数量，再在数量相同的分配中最大化总tIoU。不能为了更高总分牺牲匹配数，也不能把两次报警都算作同一个参考的检出。

`core.py`的 `match_events()`用单位容量最小费用最大流实现：每条连线容量为1，费用为负tIoU，残余路径允许撤回早先分配。初学者先能画上述连线、解释为何需要撤回，再读循环即可。运行这个小实验验证纸笔结果：

```bash
.venv/bin/python - <<'PY'
from video_temporal_audit.core import match_events

def events(intervals):
    return [dict(type='brightness_jump', start_s=a, end_s=b)
            for a, b in intervals]

p = events([(0, 6), (0, 4), (5, 9)])
t = events([(0, 5), (4, 7), (7, 9)])
r = match_events(p, t, threshold=0.25)
print(r['tp'], r['fp'], r['fn'])
print(r['matches'])
PY
```

应输出 `3 0 0`，匹配索引为 `(0,1)、(1,0)、(2,2)`；程序索引从0开始。0.25仅用于说明贪心反例，正式集合门槛仍为0.3，CLI没有 `--tiou`参数。合法门槛范围为 `(0,1]`，零、负数、布尔、NaN或无穷应拒绝。

TP是成功匹配事件，FP是未匹配预测，FN是未匹配参考。precision=`TP/(TP+FP)`，回答报警中多少匹配；recall=`TP/(TP+FN)`，回答参考中多少找到；F1=`2TP/(2TP+FP+FN)`。分母是事件数量，不是帧数或评分者人数。无预测时precision为 `null`，无参考时recall为 `null`；不能为好看而填成100%。正常片还要单列误报，不能用大量“没有异常的帧”堆高准确率。

## 八、读完整结果，保留不漂亮的部分

保存的 `examples/demo_v2/test/metrics.json`给出以下配对结果：

|事件类型|关闭补偿 TP/FP/FN|开启补偿 TP/FP/FN|参考数|
|---|---:|---:|---:|
|静止候选|2/2/0|2/2/0|2|
|亮度突变|2/2/2|2/2/2|4|
|切镜候选|4/22/0|4/0/0|4|
|合计|8/26/2|8/4/2|10|

预测数从34变12，precision从 `8/34=0.2353`变 `8/12=0.6667`；recall都是 `8/10=0.8`，F1从0.3636变0.7273。准确表述是误报减少、召回未提高。两段平移片各减少11个切镜误报，总计22个。12段参考为空的正常或反例片里，有报警的片数从4/12变2/12。

剩余4个FP和2个FN不能删掉。两段有意静止各报一次冻结，贡献2个FP；两段切镜邻近闪光各有一个未匹配亮度候选，贡献另2个FP，真正闪光参考又各漏匹配一次，贡献2个FN。某片出现亮度报警，不代表它已匹配正确闪光：区间必须达到tIoU门槛。运动补偿修好了这组平移误报，没有修好切镜保护与闪光边界的冲突。

现场展示先看平移，再看有意静止，最后看切镜邻近闪光。每次说明输入、规则、候选与参考差异，不只播放成功片。这里没有发布总体置信区间，4个声明来源组也不是独立抽样证明。历史 `reference_run`使用旧匹配协议，不能与本版分数混加。

## 九、让浏览器真的回到那个时段

静态HTML能显示文字，不意味着播放器已经成功跳转。在项目终端启动内置服务：

```bash
.venv/bin/python -m video_temporal_audit serve --directory . --port 8765
```

终端会一直运行，先不要关。浏览器访问 [首次运行时间线](http://127.0.0.1:8765/runs/first_clip/timeline.html)，等待媒体准备好，再点E001“回放此时段”。应显示定位成功，播放器从约1.5秒开始继续播放，在2秒附近出现闪光。端口被占用可改8766，网址同步修改。看完回到终端按Control+C，关闭标签不会停止服务。

HTTP Range允许播放器只请求文件的某段字节，便于随机定位；正常局部响应是206。[MDN的Range说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)解释了请求和响应。可在第二终端执行：

```bash
curl -sS -D - -o /dev/null -H "Range: bytes=0-31" \
  "http://127.0.0.1:8765/runs/first_clip/preview.mp4"
```

应看到 `206 Partial Content`与 `Content-Range: bytes 0-31/...`。这是服务检查，仍不能代替点击和观看。普通服务器不支持Range时，页面只对不超过64 MiB的预览下载并核验SHA-256，然后创建本机Blob播放；Blob可理解为浏览器持有的文件字节对象。超过上限会停止缓存，需换内置服务。双击HTML受浏览器本地读取规则影响，GitHub文件页也可能只显示源码。

既有角色18验收确实操作过修复后的浏览器：Range和普通HTTP的Blob回退都读到4秒长度、可定位区间 `[0,4]`；点击后实际时间约1.75秒且继续播放，差值来自读取时已过了一小段播放时间。本章作者没有重复这次UI验收。JavaScript协议断言、FFmpeg解码和真实浏览器点击各证明不同层，不能互相替代。

复核前正常速度看完整片，再为候选选“确认是问题、合法变化、证据不足”，填写时间和画面依据。保存本机草稿只在当前浏览器和地址恢复；导出JSONL后还要确认文件存在。用实际下载路径执行：

```bash
.venv/bin/python -m video_temporal_audit import-reviews \
  --report runs/first_clip/report.json \
  --reviews "$HOME/Downloads/实际下载的复核文件.jsonl" \
  --output runs/first_clip_reviewed
```

一个完成事件应得到 `imported=1, reviewed=1, pending=0`。新报告的 `human_reviews`保留意见，算法候选仍在。复核同时绑定片段ID、媒体摘要、有效配置摘要和事件摘要；E001只是片内编号，不能跨片复制。八个字段都须为字符串，未知事件、重复行、空依据、错摘要会拒绝。输出必须为新的独立目录，不得放进原报告内部。个人意见标为 `human_unverified`，不自动修改参考标签或重算事件分数；自动测试填写的意见更不是真人质量评分。

## 十、把故障当作学习材料

第一种故障是路径和环境错。`No module named...`时先看 `pwd`与使用的解释器，使用同一 `.venv/bin/python -m pip`检查依赖；“输入不存在”先核对引号里的完整路径。输出非空被拒绝是保留历史的保护，换新目录即可，不能打开旧报告冒充本次成功。

第二种是时间与媒体边界。当前最多1200帧、单帧像素总数不超过 `4096×2160`；这是总像素限制，不是宽高各自上限。30fps的40秒已达帧上限。坏MP4、只有音轨、重复PTS、源分辨率中途改变会失败。定位时先读终端错误，再用小副本复现；需要拆片或重编码时，记录源文件与截取偏移，不能默默转成恒定帧率来隐藏问题。

第三种是“有结果但证据错”。本轮曾发现修改报告阈值后仍能沿用旧摘要导入，以及未知既有复核造成待办数为负。修复现在会回算配置与事件绑定、校验已有复核，在复制前拒绝。非字符串事件ID原先可能崩溃，现在明确报错退出2。遇到拒收应恢复正确版本，不应手改SHA使其强行通过。

第四种是可见的算法局限：弱纹理跟踪失败、有意静止误报、切镜附近闪光漏匹配。定位它们要看 `frames.csv`的 `motion_status`、原始差与补偿残差，再回放原片。增加一次成功运行不能消除这些限制；应保留反例，提出只改变一个条件的新实验。

## 十一、练习、参考答案与四周验收
